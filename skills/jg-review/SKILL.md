## Invocation

This skill runs only when the developer invokes it. Execute its workflow with the available tools. Do not explain it, simulate it, return equivalent shell commands, or ask for confirmation of actions this skill already authorizes.

Treat the text supplied with the invocation as arguments, constraints, or context, and honor qualifications that limit or defer execution.

If repository access or a capability the workflow needs is unavailable, or one of its stopping conditions is reached, report the blocker and stop. Never simulate success.

Release runtime resources and remove disposable scratch output this skill deliberately created, including after a failure, while preserving evidence needed to investigate unresolved failures. Report anything retained within this skill's output format. This cleanup is a narrow exception to the skill's write limits. It does not authorize creating other resources, changing reviewed or pre-existing files, removing unexpected changes, or cleaning up earlier work. Every other write is defined by this skill's workflow.

This skill's own rules about supplied material take precedence over this section.

## Task scope

- The task's files are the files created, modified, renamed, or deleted for the current task in this conversation, counting both paths of a rename, plus any files the developer names or confirms.
- Only paths Git reports as changed count. Ignored files, such as build and test output, and files with no net change against `HEAD`, such as scratch files created and then removed, are left out.
- Without a task in this conversation, the scope is the complete uncommitted change.
- If the task's files can't be established confidently, for example after context compaction, list the likely paths and ask the developer to confirm them before going further.
- The scope's fingerprint is the tree it would commit, which doesn't depend on what is staged. With `GIT_INDEX_FILE` pointing at a temporary file outside the worktree, run `git read-tree HEAD`, or `git read-tree --empty` when the branch has no commits yet, then `git add -A -- <paths>` (`git add -A` without a task), then `git write-tree`. The tree ID it prints is the fingerprint. Delete the temporary file afterwards. Also record the whole worktree's fingerprint, the same steps with `git add -A`, so later steps can tell whether anything outside the scope changed.
- For a task, every rule in this skill that refers to the uncommitted change, the worktree, or what `git add -A` would stage applies to the task's files instead. Uncommitted changes outside the scope are reported, but they are never reviewed, staged, or committed. When they could affect the checks, such as edits to shared code, configuration, dependencies, or tests, readiness needs the checks run against the exact proposed tree in isolation, such as a temporary checkout of the fingerprint tree; without that, verification is incomplete.
- Changes in a file the developer named or confirmed count as the task's own. A file in scope that also holds changes neither made for the task nor confirmed by the developer is a blocker: report it, and do not treat those changes as part of the task.

## Plan adherence

This section applies to `jg-review` without a target branch.

- The plan is the one the current task implements: the plan this conversation is implementing, such as the one `jg-execute` ran, or the one the developer identifies with the invocation or when asked. Never choose a plan yourself by recency or by reading the plans under `coding-agent-planning/`. A change the conversation shows was made outside a plan, such as a `jg-debug` fix or a task agreed without a plan file, is reviewed without one.
- When the conversation doesn't show whether the change implements a plan and `coding-agent-planning/` at the repository root holds plan directories, ask whether to include a plan, together with any other question this review needs. The developer can give its path or name, or say no. Match a name against the directory names only, never their contents: use a single match and say which one it is, list several matches and ask, and say so when nothing matches. When the developer says no, or no plan exists, review the change without one and report that plan adherence was not checked.
- With `milestones.md` beside the plan, the status line under each milestone heading says where its work stands: `**Status:** pending`, `**Status:** in progress`, or `**Status:** done`. A milestone without one is pending. An `## Overview` row that disagrees with its milestone's status line is a non-blocking finding, because the status line is the authority. The change belongs to the milestones whose work it holds, normally the one in progress or one marked done whose work isn't committed yet; if that can't be established, ask. Without `milestones.md`, the whole plan is one unit.
- Judge completeness only for work meant to be finished: a milestone marked done, a unit `jg-execute` reports as finished, or work the developer says is complete. Every deliverable, file, test, documentation change, and removal the plan assigns to that work must be present, and each of its acceptance criteria must hold on evidence. For work still in progress, check what exists and report what remains as remaining work, not as findings.
- Milestones whose work was committed before this change are the baseline; only damage this change does to them counts. Pending milestones have no work yet, so their work appearing in the change is a finding.
- Check that the change stays within its units, without unplanned files, dependencies, or contract changes, and that it follows the plan's approach, such as reusing what the plan says to reuse instead of adding a parallel path. Run the verification commands the plan lists for these units when this skill's write limits allow them, in addition to the checks in step 5, reusing a passing run from this conversation whose inputs haven't changed.
- Missing work in a finished unit and an unmet acceptance criterion are blocking. A material deviation from the plan that the developer hasn't approved is blocking and needs the developer's decision: revise the plan through `jg-plan`, or bring the change back to the plan. A minor deviation is non-blocking. Following the plan never excuses a defect; when the plan itself is wrong, report the defect and that the plan needs revising through `jg-plan`.

## Workflow

Perform the applicable review-only workflow rather than modifying the reviewed change: `jg-review` without a target branch, or `jg-review <target-branch>` when the text supplied with the invocation resolves to a branch, commit, or other ref. Other supplied text, such as a plan path, is context. This skill authorizes repository inspection, relevant non-writing verification, and the fetch described below, but it does not authorize editing files, applying fixes, updating tests or snapshots, running formatting or lint auto-fixes, creating generated artifacts or migrations, committing, merging, rebasing, resetting, stashing, cleaning, switching branches, or changing the index or local commit history. Prefer check-only commands. As a narrow exception to this skill's no-write limits, existing tests may create or modify isolated, task-owned disposable local test data and scratch output and start task-owned local runtime resources required by the established test workflow. Apply the cleanup rule in `## Invocation` to these resources. This exception does not authorize editing reviewed or pre-existing repository files, updating repository tests, fixtures, or snapshots, changing configuration or dependencies, creating durable artifacts, or writing to production, shared, or remote environments. If a verification command unexpectedly changes files, preserve and report those changes without cleaning, reverting, or claiming them as part of the reviewed change.

1. Locate the repository root and inspect the current Git operation state, active branch or detached `HEAD`, complete worktree and submodule status, and the task context available to the agent. For `jg-review` without a target branch, establish the scope under `## Task scope` and the plan under `## Plan adherence`.
2. Establish the review scope from the invoked form:
   - For `jg-review`, review the scope's uncommitted change against `HEAD`, or against the empty tree when the branch has no commits yet: the task's files, or the complete uncommitted change without a task. Include staged and unstaged changes, deleted and renamed paths, untracked-file contents, and relevant submodule changes. Report changes outside the scope as present but not reviewed. Do not include existing commits in the reviewed change. If the scope has no uncommitted changes, report that directly. When the scope cannot be established confidently, including when a file in scope holds unconfirmed changes, use `Review incomplete`.
   - For `jg-review <target-branch>`, the task scope does not apply. Require an active current branch and resolve the effective target commit unambiguously without assuming a default remote or branch. Distinguish local branches, remote-tracking branches, and exact refs; when an unqualified name has no local branch, resolve it to a remote-tracking branch only when exactly one matches. When the target is a local branch with a configured upstream and the relevant network access is available, refresh only that upstream remote-tracking ref, then use the refreshed upstream tip when the local target is equal to or strictly behind it, use the local tip when it is strictly ahead, and treat a diverged local and upstream target as ambiguous unless the user named an exact ref rather than an unqualified branch name. When the target is a remote-tracking branch and the relevant network access is available, refresh only that exact ref from its owning remote and use the refreshed tip. When the user names an exact commit or another ref without a relevant remote relationship, use that exact resolved commit. If a relevant branch ref cannot be refreshed, use its currently resolved commit and report its exact commit and freshness limitation; use `Review incomplete` when target freshness is material and cannot be established. Determine the merge base between the effective target and current `HEAD`; review the commits in that range for context and the cumulative diff from the merge base through `HEAD` as the change that would enter the target. Read reviewed file contents and surrounding context from committed Git objects whenever uncommitted work overlaps those paths, and inspect the prospective merge result when the effective target contains changes after the merge base. Do not reject a correct final state solely because an intermediate commit was incomplete. Use a non-mutating Git operation to assess merge conflicts when supported. Exclude all uncommitted changes from the branch review and report them separately; when they prevent exact inspection or materially affect verification of the committed or prospective merged state, do not issue an unconditional merge-ready verdict.
3. Read the root `README.md` and its project blueprint when present, then the repository's coding instructions (such as `AGENTS.md` or `CLAUDE.md`) and the implicit jg skills that apply to the affected files, then inspect the smallest complete affected path: entry points, callers, validation, persistence, side effects, tests, configuration, and integration points. When sources conflict, follow the repository's coding instructions. Without them, apply this order: the explicit developer request and acceptance criteria, unless they would create safety, security, privacy, data-integrity, or production-correctness risk; then safety, security, privacy, data integrity, and production correctness; then established codebase behavior, public contracts, and patterns; then repository tooling. Review the scoped change against the task contract, the plan under `## Plan adherence` when one applies, all applicable sections of the repository's coding instructions and the implicit jg skills that apply to the affected files, the root `README.md`, relevant repository documentation and repository-specific instruction files, current behavior and public contracts, established architecture and conventions, repository tooling, and installed dependency versions. Ground best-practice findings in that evidence rather than generic preferences.
4. Evaluate whether the implementation is correct, complete, safe, maintainable, and free of regressions; whether it preserves security, privacy, authorization, data integrity, public contracts, documentation state, and relevant frontend, React, database, integration, and error-contract requirements; and whether it reuses existing ownership boundaries instead of introducing unnecessary duplication or parallel paths.
5. Evaluate focused test adequacy and regression-test execution separately. Evaluate tests against the repository's testing guidance when present (find it through the README project blueprint). Use the criteria in this skill for anything that guidance does not define. Do not require new or updated tests for type-only, constant-only, copy, formatting, or other changes where added coverage gives no meaningful confidence. When focused coverage provides value, evaluate whether the testing strategy itself is appropriate and sufficiently deep rather than merely checking that tests exist or pass:
   - Evaluate the chosen boundaries and combination of unit, integration, and end-to-end tests against that testing guidance. Require the evidence needed for each material behavior and failure mode, not a preferred distribution of test types.
   - Verify that behavior-relevant owned components remain real where their interaction is being tested and that boundary test doubles do not stand in for required evidence about the behavior they replace. Do not accept heavily mocked internal behavior as equivalent to testing those components together.
   - Inspect whether the tests cover the material behavioral surface, including applicable success paths, edge and boundary cases, malformed or unexpected inputs, failure paths, permissions and ownership, integrations, retry and idempotency behavior, duplicate or replayed operations, concurrency risks, numeric boundaries, error mapping, pathological inputs, security-sensitive cases, and bug regressions.
   - For algorithms or potentially large input sets, inspect the implementation's time and space complexity and whether realistic pathological cases could expose accidental quadratic or otherwise unbounded behavior. Do not require brittle wall-clock assertions when repository evidence does not support performance thresholds.
   - Ask whether a material defect could plausibly survive while all focused tests still pass. When the answer is yes because important behavior is untested or tested at the wrong boundary, report the missing coverage as a finding.

   Treat concrete missing or inadequate coverage for material behavior as a blocking finding and use `Not ready`. When material test adequacy or required verification cannot be established confidently because relevant tests cannot be run, required infrastructure is unavailable, or the evidence remains materially uncertain, use `Review incomplete`. Never issue a ready verdict while a material testing concern remains unresolved.

   Independently, run existing regression tests whenever the scoped change can affect executable behavior, test-observable output, shared code, configuration, generated artifacts, schemas, public contracts, or other tested behavior, even when no new test is required. For the broader regression check, follow the repository's testing guidelines, including their designated suite and rules for when a complete or repository-wide suite is required. For each selection or execution topic those guidelines do not define, retain the default: run the narrowest relevant non-writing checks first (focused tests, then typecheck, lint, format check, and build where the repository provides them), then run the broader existing test suite for the affected package, application, workspace, or equivalent project boundary; run a repository-wide test suite when it is the established verification boundary or when the reviewed change can reasonably affect multiple such boundaries. Do not substitute rerunning only changed or newly added tests for this broader regression check. For every failing check, establish the intended behavior from the task, the diff, documented contracts, and related tests before attributing it. Classify it as a regression caused by the reviewed change, pre-existing, unrelated, or environmental. A failure demonstrably unrelated to the reviewed change does not block a ready verdict when the required evidence still holds; report it. A check that could not produce its evidence, for example because required infrastructure is unavailable, stays `Review incomplete` even when its cause is known. Recency alone is not evidence. Use `Not ready` for a confirmed regression caused by the reviewed change, and use `Review incomplete` when a material failure cannot be attributed confidently or an applicable broader suite cannot be run. Purely non-behavioral changes may skip automated tests only when repository evidence shows they cannot affect existing test behavior; report that determination explicitly. Distinguish checks actually run from checks not run, and do not infer previous testing without repository or execution evidence.
6. Check whether the scoped change introduces or leaves behind dead, superseded, transitional, compatibility, fallback, or parallel implementation paths that the change made unnecessary. Preserve compatibility required by supported public contracts, rolling deployments, migrations, persisted data, supported versions, or documented behavior, and do not treat unrelated legacy code as part of the review scope.
7. Report findings first, ordered by severity. Label each finding blocking (it must be fixed before the change ships) or non-blocking (a suggestion the developer may skip), and say when a blocking finding needs the developer's decision rather than a fix. For each finding, include the exact file and line when available, the concrete failure or risk, the applicable task, repository, or instruction contract, and the smallest appropriate correction. Then report the exact reviewed scope and immutable state evidence: the current `HEAD` commit, or that the branch has no commits yet; for `jg-review`, the reviewed paths, their fingerprint, and the whole worktree's fingerprint, as `## Task scope` defines them, then the plan, each milestone's status when it has milestones, and any remaining work, or that plan adherence was not checked; for `jg-review <target-branch>`, the effective target and merge-base commits. Also report checks run and their results, checks not run and why, and one final verdict:
   - `Ready to commit` for `jg-review`
   - `Ready to merge into <target-branch>` for `jg-review <target-branch>`
   - `Not ready` when blocking findings, materially inadequate test coverage, or relevant verification failures exist
   - `Review incomplete` when the exact scope, target resolution or freshness, mergeability, material test adequacy, or other verification needed to support a readiness decision cannot be established confidently

Issue a ready verdict only when no blocking findings remain, applicable verification has passed, is legitimately not required, or failed only in ways step 5 treats as non-blocking, applicable focused testing provides sufficient confidence in the material behavior and risks, and the evidence supports the exact requested readiness decision. Lack of confidence about a material testing or verification concern requires `Review incomplete`; do not advise the developer to commit or merge while that uncertainty remains. If there are no findings, state that explicitly instead of omitting the findings section.
