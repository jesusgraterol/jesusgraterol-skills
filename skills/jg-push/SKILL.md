## Workflow

Execute the repository-publication workflow through completion unless one of the blocking conditions below requires stopping. `jg-push` is a skill, not the literal `git push` shell command, and it must not be reduced to running `git push`, generating shell commands, or describing what the user should run.

The mandatory execution sequence is:

1. Resolve the active branch's exact push remote and destination branch before changing Git state.
2. When any uncommitted changes exist, inspect them as required below, then stage the complete worktree with `git add -A`. This must include all staged, unstaged, untracked, deleted, and renamed changes; never selectively stage a subset for this skill.
3. Create the new commit from that complete staged state using the rules under `## Commit rules`. The commit command must end with `-s -S`; both the sign-off and cryptographic signature are mandatory.
4. Push only the active branch's current `HEAD` to the resolved remote and destination branch using an explicit one-branch refspec. Do not rely on an implicit or multi-ref push.

These steps are the authoritative meaning of `jg-push`; the detailed rules below only determine how to perform them safely and when execution must stop. When no uncommitted changes exist, do not create an empty commit and use the push-only path only for the exact intended unpublished commits established under the rules below.

Reuse repository context, change analysis, and successful verification only when the exact commits, current `HEAD`, destination, and applicable state evidence still match. A previous `Ready to commit` verdict from `jg-review` is conclusive readiness evidence while its exact `HEAD` and state fingerprint match; do not repeat the review in that case. Discard stale positive readiness evidence, but retain previously reported blocking findings or incomplete conditions until the affected current state has been inspected specifically to confirm their resolution. Do not perform a full review, broad repository exploration, or repeat checks solely because this skill was invoked.

1. Locate the repository root and gather, in as few read-only Git invocations as practical, the active branch or detached `HEAD` state, current Git operation and conflict state, complete worktree status, configured upstream and remotes, existing local commits not represented by relevant known remote-tracking refs, and recent commit subjects only when needed to infer the commit convention. Inspect submodule details only when the worktree or unpublished commit range contains a submodule change. Reuse information already established during the current task instead of rediscovering it.
2. Resolve the active branch's intended push remote and destination branch from branch-specific push configuration, repository-level push configuration, the configured upstream, repository context, and any existing remote branch; do not assume that the tracking upstream is always the push destination. Require one unambiguous remote and destination branch before staging, committing, or pushing.
3. Establish one execution path:
   - Use the commit-and-push path when uncommitted changes exist. Treat any existing unpublished commits as a separate push range rather than part of the new commit's cohesive purpose.
   - Use the push-only path when no uncommitted changes exist and the exact local commit or commit range is already established as intended for the resolved destination. This includes the exact verified commit preserved after a previous execution of this skill failed to push to the same destination.
   - When an unpublished commit or commit range has not already been established as expected for the resolved destination, inspect its exact hashes, complete commit messages, and the changed contents represented by each commit, using a commit-by-commit diff or equivalent history inspection in as few invocations as practical. Use the cumulative diff to understand the final effect, but do not use it as the sole security inspection because content introduced and later removed remains in the pushed history. Proceed only when every unpublished commit is intentional for the destination and the inspected history contains no secrets or sensitive data. The range may contain multiple independently cohesive commits and does not need one shared purpose.
   - When neither uncommitted changes nor expected unpublished commits exist, report that there is nothing to commit or push and stop without treating it as a failure.
4. For the commit-and-push path, when matching reusable analysis already covers the uncommitted change's cohesive purpose, unintended files, and possible secrets or sensitive data, confirm the current state fingerprint and inspect only the concise path and diff summary needed to compose the commit message and confirm the expected scope. Otherwise, inspect the complete uncommitted change once, including staged and unstaged changes, deleted and renamed paths, untracked-file contents, and relevant submodule changes. Independently, for any unpublished commit range in either execution path, reuse prior analysis only when it covers the exact commit hashes and destination; otherwise inspect it as required by item 3. Do not require the complete unpublished range to share one purpose. Do not expand either inspection into the correctness and readiness analysis owned by `jg-review`, and do not reread the root `README.md` or repository documentation unless the commit convention, expected commit range, or destination cannot otherwise be resolved.
5. Stop before committing or pushing when there are unresolved conflicts or an in-progress merge, rebase, cherry-pick, or revert; `HEAD` is detached; a changed or unpublished submodule state cannot be safely represented and published; the uncommitted change or any unpublished commit history appears to contain secrets or sensitive data; a relevant verification failure is known; a previously reported blocking review finding or incomplete condition remains unresolved for the state being published; the destination is ambiguous; any unpublished commit is not established as intentional for that destination; or the uncommitted changes cannot form one cohesive new commit.
6. This skill itself adds no new verification requirements and must not initiate tests, linting, typechecking, formatting, builds, or the `jg-review` workflow. Reuse successful relevant checks associated with the exact affected inputs or commit tree. If verification already required by the task, the repository's coding instructions, or an explicit repository commit or push workflow is missing, stale, or failed, stop before staging, committing, or pushing and report the specific blocker; do not run or waive the check. Checks assigned to commit or push hooks run through those hooks, not separately in advance; do not disable hooks or bypass their failures.
7. For the commit-and-push path, after publication prerequisites are satisfied, establish the exact expected commit state. Record the current `HEAD` commit and reuse the most recently confirmed state fingerprint only when no applicable input has changed since it was computed; otherwise recompute the same staging-insensitive fingerprint for the complete state that `git add -A` would stage. From the repository root, stage the complete worktree with `git add -A`. Do not selectively stage or omit current changes.
8. For the commit-and-push path, recompute the same canonical state fingerprint from the staged index and require exact equality with the expected commit state, including paths, contents, modes, symlink targets, deletions, and submodule gitlinks. A matching path set or diff summary alone is insufficient. If the fingerprint differs, do not commit; discard stale analysis and inspect the changed content before re-establishing the expected state. When it matches, record the staged tree object identifier, compose the message under `## Commit rules`, and create the commit with one or two `-m` arguments as appropriate, ending the command with `-s -S`. Inspect the created commit once and confirm its hash, expected message, expected path set, required sign-off trailer, successful cryptographic-signature verification, a clean worktree, a tree object identifier exactly matching the staged tree recorded before committing, and a parent exactly matching the `HEAD` recorded before staging. If signing, hooks, or tooling fail; the commit parent, tree, paths, or metadata differ from the expected state; or hooks leave additional uncommitted changes, do not push and report the blocker without bypassing or amending the failure.
9. Push only the active branch's current `HEAD` to the single resolved destination using an explicit one-branch refspec. Explicitly prevent tag-following or configured multi-ref behavior from publishing additional refs. If no upstream exists, establish it only as part of the same explicit push when the remote and destination branch are unambiguous. Do not fetch as a separate precondition; rely on the normal push to enforce the remote fast-forward requirement. Never assume a remote or branch, switch branches, merge, rebase, reset, stash, clean, amend, bypass hooks with `--no-verify`, or use `--force` or `--force-with-lease`.
10. Report whether this skill used the commit-and-push or push-only path, the created commit hash and subject when applicable, the pushed `HEAD` hash, active branch, remote destination, and push result. If the push is rejected or otherwise fails, preserve all local commits and clearly report the exact `HEAD` and destination so a later unchanged invocation can identify and execute the push-only retry safely.

## Commit rules

Follow the repository's established commit conventions. Otherwise use Conventional Commits `<type>(<scope>): <summary>`, deriving the type and scope from repository evidence and omitting the scope when none is accurate. Use one `-m` when the subject fully explains the change, or a subject plus one explanatory `-m` body when durable context is needed. The message must describe every staged change as one cohesive purpose. End the commit command with `-s -S`, and never bypass or drop either.
